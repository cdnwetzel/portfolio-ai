# vLLM flag experiments — prefix caching and n-gram speculative decoding (2026-09-12)

Both flags were listed as "untested, harness ready" in
[`homelab-inference-tuning-2026-08-31.md`](homelab-inference-tuning-2026-08-31.md) §"Remaining,
ranked" items 3 and 4. Neither had ever actually run. This records why, what the first real
measurements say, and what is still open.

## Why neither had run

**Three independent faults, each of which alone was enough.**

1. **conf.d never reached the launcher.** `/etc/init.d/vllm-qwen38` sourced
   `/etc/conf.d/vllm-qwen38` (OpenRC does that automatically) and used the values *inside the
   init script*, but never `export`ed them. `supervise-daemon` execs the launcher as a child,
   and a child inherits only exported variables. Measured on a process up 8d23h:
   `tr '\0' '\n' < /proc/4329/environ | grep -c '^VLLM_'` → **0**. Every variable the launcher
   reads has its own `: "${VAR:=default}"` fallback and each happened to equal conf.d, so this
   was invisible — except for `VLLM_EXTRA_ARGS`, which has no launcher default and exists
   solely to change behaviour. `--enable-prefix-caching` sat in conf.d from 2026-08-31 to
   2026-09-12 and reached nothing.

2. **The probe could not tell "instant" from "nothing."** `exp_probe.py` returned
   `(first or 0) * 1000`, so a completion that produced **zero tokens** printed as
   `TTFT 0 ms` — indistinguishable from an infinitely fast response. Same false-pass shape as
   the Aug-31 argv assertion that printed "expected for baseline" during a non-baseline run.

3. **The ngram conf.d line did not parse.** `set_extra` wrote `echo "export
   VLLM_EXTRA_ARGS=$1"`. For `prefix` the value is one shell word and that works. For `ngram`
   it is two:
   ```
   export VLLM_EXTRA_ARGS='--speculative-config' '{"method":"ngram",...}'
   ```
   bash reads that as exporting **two** names and rejects the JSON as "not a valid identifier".
   `rc-service restart` then failed with "error loading .../conf.d/vllm-qwen38" followed by
   "failed to stop" — which by luck meant the **old engine kept serving**, so there was no
   outage, but conf.d was left unparseable and every later `rc-service` call on the unit would
   have failed too.

All three are fixed: the unit exports conf.d (excluding `VLLM_PORT` — see below), the probe
returns `None` and prints `EMPTY -- 0 tokens (finish_reason=…)`, and `set_extra` shell-quotes
the whole value. The harness now also validates conf.d **before** restarting and restores the
baseline rather than proceeding (exit 8/9).

### `VLLM_PORT` must not be exported

It is also a real vLLM environment variable. `vllm/envs.py`: *"used in distributed environment
to manually set the communication port … if some code asks for multiple ports, VLLM_PORT will
be used as the first port, and the rest will be generated by incrementing"*. Exporting
`VLLM_PORT=8007` would hand the engine's internal allocator a base of 8007 and walk it into
**8008 and 8009 — the sibling backend slots**. The launcher takes `VLLM_SERVE_PORT` instead and
`unset VLLM_PORT`s before exec. Asserted post-restart: 19 `VLLM_*` vars present,
`VLLM_PORT` absent.

### Related: `respawn_delay=60` was running as 30s

Found in the same session from a start-up line that reads like boilerplate:
`supervise-daemon: Please increase the value of --respawn-delay (60000ms) to more than
--respawn-delay-cap (30000ms)`. `--respawn-delay-cap` defaults to **30s** and is active
whenever `--respawn-delay-step` is above 0 — and that defaults to 128ms. OpenRC 0.63 maps only
`respawn_delay`/`respawn_max`/`respawn_period` onto supervise-daemon arguments
(`/usr/libexec/rc/sh/supervise-daemon.sh:42-44`), so there was no way to set the cap from the
unit's normal variables. Fixed with `supervise_daemon_args="--respawn-delay-cap 60"`, verified
live in the supervisor's argv. **Swept: `vllm-qwen38` is the only affected unit** — every other
supervised unit sets `respawn_delay` ≤ 15, under the default cap.

Reproduces the 2026-08-31 numbers, so the two runs are comparable.

| probe | TTFT | decode |
|---|---|---|
| A cold (fresh prompt) | 1386 / 1325 ms | — |
| B repeated prefix | 1328 / 1330 / 1336 ms | — |
| C quoting (192 tok) | 1342 / 1354 ms | 34.3 / 34.2 tok/s |

## Prefix caching — TTFT win confirmed, correctness NOT cleared

`enable_prefix_caching=True` resolved for the first time; `--enable-prefix-caching` confirmed
in live argv.

**The win is real.** The trustworthy row is **probe C**, because both runs generated a full 192
tokens: TTFT **1342/1354 → 512/499 ms**, a ~63% reduction. Corroborated independently by vLLM's
own metric: `Prefix cache hit rate` 0.0% → 0.0% → 33.3% → 57.5% → 57.4%. Decode unchanged
(33.6/33.6/33.5 vs 34.3/34.2 — this is a prefill mechanism).

**The blocker.** Probe B printed `0 ms, 492 ms, 0 ms`. Two of those three runs produced **zero
tokens**. The same three prompts, at temperature 0, on the same model, produced 32 tokens each
at baseline — deterministic sampling, identical input, different output, so the config changed
behaviour. An empty completion reaching a user is the 2026-08-29 blank-bubble symptom, and no
TTFT gain justifies it. Consistent with vLLM 0.27.1 keeping prefix caching **opt-in for hybrid
models because the path is still maturing** (`arg_utils.py:2604` computes the default as
`is_prefix_caching_supported and not is_hybrid`).

**Resolved the same night: the empties are confined to an endpoint cwdotcom never calls.**

The second `prefix` run reproduced them exactly — the same two of three probe-B positions, both
times. But `exp_probe.py` talks to **`/v1/completions`**, a raw text completion whose prompt ends
in `"Answer:"`. The proxy sends only **`/v1/chat/completions`** with a system message,
`enable_thinking=false` and `max_tokens=2048`. Measured at production sampling (temp 0.2,
top_p 0.7, presence_penalty 0) with the flag on:

| request shape | empty completions |
|---|---|
| `/v1/completions` (not used by cwdotcom) | **25 / 30** |
| `/v1/chat/completions`, synthetic prefix | **0 / 30** |
| `/v1/chat/completions`, the REAL `SYSTEM_PREFIX` + production-shaped chunk blocks | **0 / 40** |

The last row is the one that decides it: `SYSTEM_PREFIX` read straight out of `api-proxy.py`,
five `### title (source)` chunk blocks, `SYSTEM_SUFFIX`, four golden-set-style questions x 10.
All 40 finished naturally (`finish=stop`) at 204–1339 chars. Harness:
`scripts/tuning/prefix_empty_probe.py`.

Note the inversion, because it defeats the usual intuition: on `/v1/completions` the defect is
**worse at temperature 0.2 than at 0** (item 1 went 0/3 greedy → 6/10 sampled). "It only happens
at greedy" would have been a comfortable and wrong conclusion.

Production also has two independent cushions: the proxy retries once when zero tokens were
emitted, and emits `{"type":"error"}` rather than a blank success (`cloud/api-proxy.py:844-899`).

**Verdict: favourable, PENDING a clean-pipeline re-gate before deployment.**
`--enable-prefix-caching` is in the repo launcher's permanent argv
(`home/vllm-service/start-qwen38.sh`), deliberately *not* in conf.d's `VLLM_EXTRA_ARGS` — that
is the experiment slot, and `09-vllm-experiments.sh` refuses to start when it is occupied.

**It is not deployed yet, on purpose.** Every *quality* measurement above — the 50-generation
`repeat_sample` gate, probe E, the 0/40 empties — was taken while DEFECT_LEDGER #17 was still
handing the generator compressed context. Those runs were measuring a pipeline that was broken
in a way not yet discovered, so they cannot clear a change. The *latency* numbers are unaffected
(`exp_probe.py` and `bench-vllm.sh` talk straight to vLLM :8007 and never touch the proxy).
Re-run the gate on the fixed pipeline, then promote with
`scripts/tuning/10-install-service-files.sh`.

**Do not quote −63% as the production win.** The probe shares ~1,800 prefix tokens out of a
short prompt; cwdotcom shares only the ~600-token `SYSTEM_PREFIX` plus the server-facts line,
against ~11.5K tokens of per-query KB chunks that never repeat. Turn 1 gains much less than the
probe suggests; follow-ups that resend history and re-retrieve the same chunks gain more. The
real figure has to come from the site's own `ttft_ms` telemetry.

### Second measurements from the adopted run

| | baseline | prefix |
|---|---|---|
| probe C TTFT (192 tok, trustworthy) | 1342 / 1354 ms | 503 / 491 ms |
| probe E median TTFT (n=20) | 1406 ms | 480 ms |
| probe D control (short prompt) | 176 / 203 ms | 175 / 200 ms |
| decode | 34.2–34.3 tok/s | 33.7–33.9 tok/s |
| prefix cache hit rate | 0.0% x 5 windows | 57.5 → 64.6% |
| probe E empty rate | 0/20 | 0/20 |

Decode is ~1% lower in both prefix runs. Within noise, but it is consistently *lower*, never
higher — so record it as "no decode gain, possibly a small cost", not as a wash.

The restart was **100s**, against 365s for the first prefix run. Changing the engine config
changes the `torch.compile` cache key; once an entry exists for a config, that config restarts at
normal speed. Budget the ~290s of Dynamo/inductor work once per new flag combination, not every
time.

Note for whoever re-runs it: the first `prefix` restart took **365s** versus 105s for a config
the compile cache had already seen. Changing the engine config changes the `torch.compile` cache
key, and a cold cache costs ~290s of Dynamo/inductor work. Budget for it; it is not a hang.

## n-gram speculative decoding — MEASURED 2026-09-13, **DECLINED: it is a 9% REGRESSION**

It ran properly for the first time (the conf.d quoting fault above had made every previous
attempt abort before the engine restarted). Live argv carried `--speculative-config` with the
JSON's double quotes intact, and the engine resolved
`speculative_config=SpeculativeConfig(method='ngram')`. So this is a real measurement, not
another null from a flag that never landed.

Arm: `prefix + ngram`, against the `prefix only` arm measured the night before.

| | decode (256-token bench) |
|---|---|
| baseline, no flags | 34.2 tok/s |
| prefix only | 33.8 tok/s |
| **prefix + ngram** | **30.7 tok/s — −9.2%** |

**And it lost hardest exactly where it should have won.** Probe C quotes retrieved context back
verbatim, which is the workload n-gram exists for; probe D is original prose and should be
unaffected.

| probe | prefix only | prefix + ngram |
|---|---|---|
| C, quoting | 34.1 tok/s | **25.7 tok/s (−24.6%)** |
| D, non-quoting control | 34.0 tok/s | 27.5 tok/s (−19.1%) |

One caveat on those two rows, stated rather than buried: probe C emitted **74 tokens** this run
against 192 before, so its rate is noisier and not a clean like-for-like. The 256-token bench is
clean, and it is the −9.2% that decides this.

**Hypothesis for WHY, offered as a hypothesis — not established.** This box gets its 4.4x from
`cudagraph_capture_sizes=[1,2,4,8]`, deliberately capped because capturing ~70 sizes OOMed.
Speculative decoding runs draft-then-verify with a *variable* number of tokens per step, so those
steps plausibly fall outside the captured sizes and drop to eager execution. That would explain a
roughly uniform slowdown across BOTH probes rather than a quoting-specific one, and it predicts
n-gram is structurally incompatible with this box's single largest tuning win rather than merely
unhelpful here. Testable by widening the capture sizes or grepping the engine log for graph
misses — but the test risks the thing worth 4.4x, so it is not worth running.

**Do not reopen without a mechanism.** "No draft model, no VRAM cost" was the argument for trying
it and it remains true; it is simply not the binding constraint. The binding constraint is that
acceptance has to pay for verification, and on this model at TP=2 with capped CUDA graphs it does
not. `rag-improvements.md` §2.3 ruled out the *draft-model* variant on VRAM grounds; this closes
the ngram variant on throughput grounds. Both are now measured rather than assumed.

Reverted immediately — production ran ~9% slower for the length of the experiment window.

## What this session settled about method

- **A measurement instrument that cannot represent failure will report success.** Two of the
  three faults here were instruments, not the system: a probe that coerced "no tokens" to
  `0 ms`, and an assertion that printed "expected for baseline" on a non-baseline run. Both
  produced confident, wrong, *favourable* results.
- **Validate config before acting on it, not by acting on it.** The broken conf.d was
  discovered by a failed `rc-service restart`. One `sh -c ". $CONF"` beforehand would have
  caught it with no service interaction at all. Now it does.
- **`backup_once` was a time bomb.** It skipped the copy whenever a `.orig` existed, so the
  Aug-31 backups would have made the next `revert` restore the Aug-31 launcher over the
  current one — silently undoing unrelated fixes while printing "reverted and serving".
  Replaced with a clean-baseline assertion plus an unconditional rotating backup. Confirmed
  working: the revert after the prefix run left the new launcher intact.
